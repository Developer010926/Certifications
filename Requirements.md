# Требования к системе управления контрактами и сертификациями

## 1. Назначение системы

Система предназначена для ведения сотрудников, их контрактов и сертификаций, необходимых для продления контрактов.

Система должна:

- предоставлять администраторам функции управления сотрудниками, контрактами и сертификациями;
- предоставлять сотрудникам доступ только к собственной информации в режиме чтения;
- отображать текущее состояние сертификации каждого активного сотрудника;
- хранить завершённые контракты и предыдущие сертификации;
- автоматически рассчитывать срок действия контракта и статус сертификации.

## 2. Термины

| Термин | Определение |
|---|---|
| Сотрудник | Пользователь системы, для которого обязательно создаётся контракт. |
| Активный контракт | Единственный текущий контракт сотрудника с признаком `Active = true`. |
| Архивный контракт | Закрытый контракт с признаком `Active = false`. |
| Сертификация | Запись `Prolongation`, описывающая прохождение сертификации для продления контракта. |
| Расчётная дата окончания | `ValidTo`, если оно заполнено; иначе `ContractDate + ProlongationForYears`. |
| Последняя сертификация | Сертификация с максимальным значением `CertificationDate`. |

## 3. Роли и права доступа

### 3.1. Обычный пользователь

Обычный пользователь:

- может войти в систему только при наличии активного контракта;
- после входа переходит на собственную страницу;
- видит только собственные персональные данные, активный контракт, статус и историю сертификаций;
- не может редактировать свои данные;
- может посмотреть только собственный пароль.

Страница пользователя работает в режиме `read-only`.

### 3.2. Администратор

Администратор имеет все административные права без разделения на дополнительные роли.

Администратор может:

- создавать и редактировать сотрудников;
- назначать и снимать признак `IsAdmin`;
- создавать и закрывать контракты;
- создавать и вести сертификации;
- генерировать новый пароль сотрудника;
- просматривать пароль любого сотрудника;
- просматривать таблицу сертификаций;
- просматривать собственную страницу.

У администратора, как и у обычного пользователя, должен быть активный контракт для входа в систему.

После входа администратору предлагается выбрать режим:

1. **Моя страница** — просмотр собственных данных.
2. **Администрирование приложения** — переход к административной странице сертификаций.

Система должна запоминать последний выбор администратора и использовать его как выбор по умолчанию при следующем входе.

## 4. Сотрудники

### 4.1. Создание сотрудника

Сотрудник создаётся администратором одновременно с первым контрактом в одной форме.

Создание сотрудника и первого контракта является одной атомарной операцией. Если контракт не прошёл проверку или не сохранился, сотрудник также не создаётся.

Обязательные поля сотрудника:

- `PersonalId`;
- `FirstName`;
- `LastName`;
- сгенерированный пароль.

Опциональные поля:

- `MiddleName`.

Обязательные поля первого контракта:

- `ContractDate`;
- `Position`.

Опциональные поля первого контракта:

- `Department`;
- `Division`;
- `ValidTo`.

### 4.2. Personal ID

`PersonalId` вводится администратором и используется как логин пользователя.

Требования к `PersonalId`:

- значение обязательно;
- значение должно быть уникальным среди всех сотрудников, включая архивных;
- уникальность проверяется без учёта регистра и пробельных символов;
- перед сравнением система удаляет пробельные символы и приводит значение к единому регистру;
- при обнаружении дубликата сохранение запрещается;
- администратор может изменить `PersonalId` после создания сотрудника;
- при изменении повторно выполняется проверка уникальности;
- изменение `PersonalId` немедленно изменяет логин пользователя.

### 4.3. Признак администратора

У сотрудника имеется булевый признак `IsAdmin`.

- `IsAdmin = true` предоставляет административный режим;
- `IsAdmin = false` предоставляет доступ только к собственной странице;
- администратор может назначать и снимать этот признак.

### 4.4. Архивирование сотрудника

Физическое удаление сотрудника не предусмотрено.

Сотрудник становится неактивным после закрытия его последнего активного контракта. Такой сотрудник:

- сохраняется в базе;
- получает статус `NotApplicable`;
- не может войти в систему;
- не показывается в основной таблице без специального фильтра.

## 5. Пароли

### 5.1. Генерация и смена

- Пароль генерируется системой по команде администратора.
- При создании сотрудника пароль должен быть сгенерирован до сохранения.
- Администратор может сгенерировать новый пароль в дальнейшем.
- После генерации нового пароля предыдущий пароль немедленно перестаёт действовать.

### 5.2. Требования к паролю

- минимальная длина — 8 символов;
- обязательны буквы;
- обязательны цифры;
- специальные символы разрешены, но не обязательны.

### 5.3. Хранение и отображение

Пароль должен храниться с использованием обратимого шифрования, поскольку система должна позволять повторно показать исходный пароль.

- пользователь может расшифровать и посмотреть только собственный пароль;
- администратор может расшифровать и посмотреть пароль любого сотрудника;
- ключ шифрования должен храниться отдельно от базы с зашифрованными паролями — в конфигурации приложения или специализированном хранилище секретов;
- ключ шифрования нельзя сохранять рядом с зашифрованным паролем или отображать в административном UI;
- доменное поле должно отражать фактическую семантику хранения, например `EncryptedPassword`, а не `PasswordHash`.

Обратимое хранение пароля является осознанным бизнес-требованием и отличается от необратимого хеширования.

## 6. Контракты

### 6.1. Общие правила

- У сотрудника может быть несколько контрактов за всё время работы.
- В каждый момент времени у сотрудника может быть не более одного активного контракта.
- Нельзя создать новый активный контракт, пока предыдущий активный контракт не закрыт.
- В рабочих процессах используется последний активный контракт.
- Закрытые контракты сохраняются в базе как архивные записи.
- Отдельный пользовательский интерфейс истории контрактов не требуется.
- Контракт никогда не считается бессрочным.

### 6.2. Поля контракта

| Поле | Обязательность | Назначение |
|---|---:|---|
| `ContractDate` | Да | Дата начала действия контракта. |
| `Position` | Да | Должность сотрудника. |
| `Department` | Нет | Подразделение. |
| `Division` | Нет | Более крупная организационная единица. |
| `ValidTo` | Нет | Явная дата окончания действия контракта. |
| `Active` | Да | Признак активного контракта. |
| `ProlongationWarningMonths` | Да | Порог начала подготовки к сертификации. |
| `ProlongationAlertMonths` | Да | Порог критического отсутствия сертификации. |
| `ProlongationForYears` | Да | Срок продления контракта после завершения сертификации. |

### 6.3. Настройки продления

Значения по умолчанию:

```text
ProlongationWarningMonths = 3
ProlongationAlertMonths   = 1
ProlongationForYears      = 1
```

При создании контракта эти значения автоматически заполняются значениями по умолчанию. Администратор может переопределить их для конкретного контракта.

Правила валидации:

- `ProlongationWarningMonths` и `ProlongationAlertMonths` не могут быть отрицательными;
- `ProlongationForYears` должно быть положительным;
- должно выполняться `ProlongationAlertMonths < ProlongationWarningMonths`.

### 6.4. Расчёт срока действия

Расчётная дата окончания определяется по правилу:

```text
EffectiveValidTo = ValidTo
                   если ValidTo заполнено

EffectiveValidTo = ContractDate + ProlongationForYears
                   если ValidTo не заполнено
```

Если `ValidTo` отсутствует, оно остаётся пустым в базе до завершения сертификации, однако вычисленное `EffectiveValidTo` используется:

- для отображения срока действия;
- для вычисления статуса;
- для сортировки и фильтрации.

### 6.5. Закрытие контракта

При закрытии контракта:

- `Active` устанавливается в `false`;
- если `ValidTo` не заполнено, система устанавливает фактическую дату закрытия;
- контракт сохраняется как архивный;
- новый активный контракт можно создать только после успешного закрытия предыдущего.

## 7. Сертификации

### 7.1. Создание

Сертификация создаётся администратором для активного контракта.

При создании обязательны:

- `CertificationDate` — дата сертификации;
- `Assessor` — экзаменатор.

Название поля должно быть `Assessor`, а не `Accessor`.

Нельзя создать новую сертификацию, если предыдущая сертификация этого контракта не завершена и имеет статус `CertificationInProgress`.

Последней считается сертификация с максимальной `CertificationDate`.

### 7.2. Этапы процесса

Сертификация проходит этапы в следующем порядке:

```text
CertificationDate
→ ProtocolDate
→ ProlongationSend
→ ProlongationReturned
```

Назначение полей:

| Поле | Назначение |
|---|---|
| `CertificationDate` | Дата проведения сертификации. |
| `ProtocolDate` | Дата протокола после прохождения сертификации. |
| `ProlongationSend` | Дата отправки результата в другой отдел. |
| `ProlongationReturned` | Дата возврата обработанного результата. |

Система не отправляет сообщения и не взаимодействует с другим отделом. Она только фиксирует даты отправки и возврата.

### 7.3. Проверка дат

Должны выполняться правила:

```text
CertificationDate <= ProtocolDate
ProtocolDate      <= ProlongationSend
ProlongationSend  <= ProlongationReturned
```

- Последующее поле нельзя заполнить без заполнения предыдущего.
- До завершения сертификации администратор может исправлять даты задним числом, если хронологический порядок сохраняется.
- Заполнение `ProlongationReturned` завершает сертификацию.
- После завершения запись блокируется и больше не редактируется.
- Очистить `ProlongationReturned` или вернуть завершённую сертификацию в работу нельзя.

### 7.4. Завершение и продление

При сохранении `ProlongationReturned` система атомарно выполняет:

```text
Contract.ValidTo = Prolongation.ProtocolDate
                   + Contract.ProlongationForYears

CertificationStatus = ContractValid
```

После этого сертификация остаётся в истории, а следующий цикл статусов рассчитывается от нового `ValidTo`.

История сертификаций отображается на странице контракта в виде списка `ProlongationRow`.

## 8. Статусы сертификации

### 8.1. Перечень статусов

| Статус | Значение |
|---|---|
| `NotApplicable` | У сотрудника нет активного контракта; статус сертификации не рассчитывается. |
| `ContractValid` | До начала периода сертификации ещё достаточно времени либо сертификация успешно завершена. |
| `CertificationPending` | Наступил период подготовки, но новая сертификация ещё не создана. |
| `CertificationInProgress` | Имеется незавершённая сертификация. |
| `CertificationMissing` | Наступил критический порог, а незавершённая сертификация отсутствует. |

### 8.2. Приоритет и алгоритм расчёта

Статус рассчитывается для сотрудника и его последнего активного контракта в следующем порядке:

```text
1. Если активного контракта нет:
   NotApplicable

2. Если существует незавершённая последняя сертификация:
   CertificationInProgress

3. Если Today < EffectiveValidTo - WarningMonths:
   ContractValid

4. Если Today >= EffectiveValidTo - WarningMonths
   и Today < EffectiveValidTo - AlertMonths:
   CertificationPending

5. Если Today >= EffectiveValidTo - AlertMonths
   и незавершённой сертификации нет:
   CertificationMissing
```

`CertificationInProgress` имеет приоритет над календарными порогами и сохраняется даже после достижения `AlertMonths` или истечения контракта.

После успешного возврата сертификации `ValidTo` пересчитывается, а статус становится `ContractValid`.

Границы периодов включаются в новый статус: в день достижения порога `WarningMonths` устанавливается `CertificationPending`, а в день достижения `AlertMonths` — `CertificationMissing`, если нет незавершённой сертификации.

## 9. Пользовательский интерфейс

### 9.1. Вход

- Пользователь входит по `PersonalId` и паролю.
- Сотрудник без активного контракта не допускается в систему.
- Обычный пользователь сразу переходит на собственную страницу.
- Администратор получает выбор между собственной страницей и административным режимом.

### 9.2. Таблица сертификаций

Основная административная таблица содержит одну строку для одного активного сотрудника и отображает:

- данные сотрудника;
- последний активный контракт;
- расчётную дату окончания контракта;
- последнюю сертификацию по максимальной `CertificationDate`;
- текущий рассчитанный статус.

По умолчанию сотрудники без активного контракта не показываются. Для их отображения используется специальный фильтр; их статус равен `NotApplicable`.

Таблица должна поддерживать сортировку и фильтрацию как минимум по:

- имени и фамилии;
- подразделению;
- сроку действия контракта;
- статусу сертификации.

### 9.3. Страница сотрудника и контракта

Административная форма должна позволять:

- создавать и редактировать сотрудника;
- изменять `PersonalId`;
- назначать или снимать `IsAdmin`;
- создавать и закрывать контракт;
- генерировать и показывать пароль;
- создавать сертификацию;
- просматривать список предыдущих сертификаций.

Личная страница сотрудника показывает те же относящиеся к нему данные без возможности редактирования.

## 10. Транзакционность и проверки

Атомарно должны выполняться следующие операции:

1. Создание сотрудника вместе с первым контрактом.
2. Завершение сертификации вместе с пересчётом `Contract.ValidTo`.
3. Закрытие текущего контракта перед созданием нового активного контракта.

Система должна запрещать сохранение при нарушении хотя бы одного из правил:

- дублирующийся нормализованный `PersonalId`;
- отсутствие обязательных полей;
- более одного активного контракта у сотрудника;
- создание сотрудника без контракта;
- создание новой сертификации при наличии незавершённой;
- нарушение порядка дат сертификации;
- некорректные настройки порогов продления.

## 11. Требования, не входящие в объём системы

В текущий объём не входят:

- физическое удаление сотрудников;
- отдельный UI истории контрактов;
- отправка сообщений или документов в другой отдел;
- интеграция с внешней системой другого отдела;
- различные уровни административных ролей;
- пользовательское редактирование собственных данных;
- аудит изменений.

## 12. Критерии приёмки

Система соответствует требованиям, если:

1. Нельзя создать или изменить сотрудника с повторяющимся нормализованным `PersonalId`.
2. Нельзя создать сотрудника без первого валидного контракта.
3. У сотрудника не может быть более одного активного контракта.
4. Пользователь без активного контракта не может войти.
5. Обычный пользователь видит только собственную страницу в режиме чтения.
6. Администратор может выбрать личный или административный режим, и последний выбор запоминается.
7. Пароли генерируются по заданной политике, шифруются и доступны только уполномоченным пользователям.
8. Новый пароль немедленно отменяет предыдущий.
9. Статусы рассчитываются согласно установленным порогам и приоритетам.
10. Незавершённая сертификация всегда имеет статус `CertificationInProgress`.
11. Нельзя создать вторую сертификацию до завершения первой.
12. Нельзя нарушить последовательность дат сертификации.
13. Завершение сертификации обновляет `ValidTo` по утверждённой формуле и возвращает статус `ContractValid`.
14. Завершённую сертификацию нельзя изменить или вернуть в работу.
15. Основная таблица показывает последнее состояние каждого активного сотрудника и поддерживает требуемые фильтры и сортировку.
